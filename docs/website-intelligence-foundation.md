# Website Intelligence Engine foundation

This document describes the incremental foundation added around the existing Fatorati scanner. It does not replace the crawler, URL parser, finding/score implementation, Markdown rendering, or static site.

## What is live today

- Public pages remain statically generated by Astro. The public no-account scan still uses the existing Pages Function, browser report, crawler, parser, PageSpeed integration, and crawl-derived topic/question evidence.
- Every API request receives a fresh request ID. `POST /api/scan` returns it in `X-Request-ID`. A `prepare` request also returns a server-created `scanId` in JSON and `X-Scan-ID`; browser page batches carry that ID forward. The ID is correlation metadata, not authentication or a secret.
- JSON logs contain an event name, environment, request/scan IDs, and bounded scalar counts or reason codes. They deliberately omit submitted URLs, IP addresses, page text, JWTs, API keys, raw errors, and request bodies.
- `ScanLimiter` preserves the existing limits—2 prepare requests and 20 page-batch requests per 10 minutes per IP—behind an interface. The implementation is bounded and isolate-local, not a distributed quota.
- The current public form does not sign users in, provide a project ID, or send an Auth JWT. It therefore remains stateless. Its reports and browser-computed findings are not saved.
- An opt-in backend persistence path exists for a future authenticated caller: it needs the feature flag, Supabase configuration, a Supabase Auth bearer token, and an owner-visible project whose stored domain matches the submitted site. It uses the caller token and Supabase RLS; failed/unavailable persistence is skipped and the scan response still succeeds. At present, the API can persist crawl-page rows, but the existing browser-computed finding list is not submitted or persisted. There is no login, project-management, or saved-report UI.

## Cloudflare Pages environments

`wrangler.toml` uses the supported Pages Wrangler environments:

| Runtime | Wrangler environment | `APP_ENV` | Persistence default |
| --- | --- | --- | --- |
| Local development | root configuration | `development` | disabled |
| Staging / preview deployments | `env.preview` | `staging` | disabled |
| Production | `env.production` | `production` | disabled |

Cloudflare Pages exposes `preview` and `production`; this project intentionally does **not** define an unsupported `env.staging`. Treat the Pages Preview environment as staging. Public Astro output remains static; the Pages Function serves `/api/scan`.

### Runtime variables

Set variables in the relevant Cloudflare Pages **Functions runtime environment**, not browser-side Astro variables such as `PUBLIC_*`.

| Variable | Required? | Purpose and handling |
| --- | --- | --- |
| `APP_ENV` | Set per environment | Labels structured logs as `development`, `staging`, or `production`. Unknown values are reported as `unknown`. |
| `GOOGLE_PAGESPEED_API_KEY` | Optional | Keep as a Cloudflare secret. Without it, the existing PageSpeed call can still run subject to Google's unauthenticated quota. Never put the key in browser code or commit it. |
| `SCAN_PERSISTENCE_ENABLED` | No; defaults to `false` | Must be exactly `true` (case-insensitive) to attempt optional persistence. Keep disabled until an authenticated product flow is intentionally enabled. The checked-in Wrangler value is `false` for all environments. |
| `SUPABASE_URL` | Required only when persistence is enabled | HTTPS Supabase project URL. HTTP is accepted only for local development on loopback. Do not include a path, credentials, query, or fragment. |
| `SUPABASE_ANON_KEY` | Required only when persistence is enabled | Supabase publishable/anon key used by the server-side adapter. It is not a service-role key. Keep it in the Functions runtime rather than exposing it through the public frontend. |
| Supabase Auth access token | Required per persisted request | Sent as `Authorization: Bearer …` by an authenticated caller. It is forwarded only to the configured Supabase REST endpoint; Supabase validates it and applies RLS. It is never logged. |
| `projectId` | Required on an authenticated `prepare` request | Must identify a project visible under the caller's RLS identity. The function also compares its stored domain with the scanned host before creating a scan. It is not an owner identity. |

The scanner does not read a service-role key, and Cloudflare Access editor claims, `ADMIN_EMAILS`, or the editorial dashboard identity are not used as a scanner-user identity. Do not enable the flag merely because the editorial dashboard is protected by Cloudflare Access. The project-domain comparison is a scope guard, not proof that the caller controls that public domain; the scan still requires the existing permission confirmation, and a future owner workspace should define an explicit domain-verification process. To intentionally enable the optional path, update the appropriate Wrangler environment flag and configure the matching Supabase variables in the Cloudflare environment; then test the full Auth/RLS flow before production use.

## Supabase migration and access model

Migration: `supabase/migrations/20261005000000_initial_scan_foundation.sql`.

It creates only four tables:

- `projects`: `auth.users` owner, domain, name, and active/archive state.
- `scans`: project, lifecycle status, scanner version, page limits, counts, and timestamps.
- `crawl_pages`: bounded page URL, response, metadata, heading, and crawl timestamps. It stores no HTML body.
- `findings`: a compact extensible finding record with category, severity, explanation, JSON evidence, confidence, recommendation, and an optional page relation.

Indexes support owner/project, scan, URL, and page-level lookups. Checks bound common text, confidence, severity, statuses, page counts, and heading JSON. A finding's optional page must belong to the same scan. No tables are added for keywords, Search Console, analytics, SERPs, backlinks, AI, or business data.

RLS is enabled on every table. Anonymous access is revoked. Authenticated table operations are scoped to the project owner via `auth.uid()`; child scans, crawl pages, and findings inherit that owner boundary through their parent rows. The repository uses the caller's bearer token plus the anon key so RLS remains active. It does not use a service-role bypass. The code caps stored page batches at 10, reads up to 100 pages and 500 findings per scan, bounds response bodies to 1 MB, limits repository requests to four seconds, and rejects out-of-range inputs.

Apply the versioned SQL through the Supabase SQL Editor or a linked Supabase CLI workflow after reviewing it for the target project. This repository includes the migration file but does not include a Supabase project ID, database credentials, local Supabase config, or an already-linked remote project. No migration was applied to a live database in this implementation.

### Persistence lifecycle and limits

1. An authenticated caller submits `projectId` with `prepare`. The API reads the project through RLS, checks that its domain matches the scan host, and creates a `running` scan with the server-generated scan ID.
2. Each page batch carries that `scanId` and the caller JWT. The API re-reads the scan/project through RLS, verifies the domain again, and upserts the bounded crawl-page records. The final batch sets `finalBatch: true` and marks the scan complete.
3. The no-account browser flow sends correlation IDs and a final-batch flag, but no JWT or project ID; it therefore does not persist. Supabase failures in an authenticated opt-in flow are logged only by safe reason/status fields and do not fail the scanner response.

This is a foundation, not a complete saved-report product. Browser-computed findings and PageSpeed results are not persisted. There is no project-creation endpoint/UI, user-authentication flow, saved-report retrieval UI, transaction spanning an entire scan, retention schedule, stale-running-scan cleanup, or user deletion workflow. An interrupted or partially failed optional write can leave a `running` scan or partial crawl-page rows. Add a deliberate lifecycle and retention design before collecting user data at scale.

## Provider-independent intelligence contracts

`functions/_shared/intelligence-contracts.ts` defines source/provenance, observed metric, inferred crawl evidence, provider availability, and human-reviewable opportunity shapes. It contains no provider client, data, credential, prediction, or integration.

The existing `functions/_shared/search-intelligence.ts` remains the source for current query normalization, intent/modifier interpretation, page-role evidence, and crawl-derived question patterns. Crawl inference remains labeled as inferred. External observations require their source and collection/period provenance; confidence describes the strength of an interpretation, not a ranking, traffic, conversion, or business-outcome probability. A reviewable opportunity is not an automatic page creation, merge, redirect, or guaranteed benefit.

Search Console, analytics, keyword research, SERP, backlink, AI, and business-data providers remain disconnected. Do not populate these contracts with sample values and present them as measured data.

## Security and operational limits

- The current scan URL validation, same-site checks, manual redirect handling, response/body limits, time budgets, concurrency caps, and public-hostname checks remain in the existing scanner. This foundation adds no alternate crawler or URL parser.
- **DNS resolution is not pinned to verified public IP addresses.** Hostname checks do not prove that a hostname resolves only to public addresses, and DNS-rebinding/private-address resolution is not mitigated by this change. Do not describe this scanner as DNS-rebinding protected or use it as a security scanner. Safe DNS/egress hardening needs a separate design within the existing fetch path.
- The in-memory limiter is per isolate and can reset, multiply across isolates, or be bypassed by distributed clients. Keep Cloudflare WAF/account-level rate limiting on `/api/scan` for production use; the code hook is not a global quota.
- Rate limits are two prepare requests and 20 page batches per IP in each 10-minute window, enforced best-effort per isolate. Sitemap discovery is limited to 15 seconds overall, six sitemap files, and 5,000 URL entries; an individual discovery fetch times out after three seconds. A scan checks at most 100 public pages, in batches of up to 10, with at most four page fetches concurrently; each page fetch times out after five seconds. HTML is capped at 350 KB per page, sitemap responses at 1 MB, and each request body at 18 KB. PageSpeed runs only on the submitted URL, has a 20-second request timeout, and remains subject to Google's quotas.
- The scanner does not render client-side JavaScript. JSON-LD checking remains syntax-only; absence is optional and unscored. It does not establish Schema.org validity, rich-result eligibility, rankings, or AI-search inclusion.
- Structured logs intentionally exclude submitted URLs, IPs, content, and credentials. Request/scan IDs are correlation values, not identity or authorization.
- A real Supabase migration/database integration, Cloudflare deployment, DNS hardening, global rate limit, and live-provider behavior were not exercised by unit tests in this repository.

## Recommended next phase

First define and implement general scanner-user authentication and project lifecycle: Supabase Auth session handling, project creation/domain normalization and verification policy, saved-report access/deletion, retention, cleanup of interrupted scans, and integration tests against a local Supabase/Postgres instance proving cross-owner RLS denial. Then expose an explicit saved-report UX and privacy/retention terms. Only after that boundary is stable should a first external provider be selected and connected with actual credentials, consent, source provenance, quotas, and evidence-based review rules. Search Console is a reasonable first candidate if its account authorization and scope can be implemented deliberately; it is not connected by this foundation.
